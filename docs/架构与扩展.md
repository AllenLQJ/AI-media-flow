# 架构与扩展

## 模块职责

| 模块 | 职责 | 扩展方式 |
|---|---|---|
| CLI / workflows | 稳定操作入口、业务状态与审核门禁 | 新总控调用相同 CLI；生成始终经过同一门禁 |
| domain | 需求校验、最终请求编译、审核 schema、能力参数校验 | 调整模型编译方式时更新 compiler_version 并重新审核 |
| skills | 五个项目 Skill 的文本与内容版本 | 改 SKILL.md 或 request.template.txt；修订工作流、重新审核 |
| gateways | HubGateway 接口、标准 stdio MCP、原始状态映射 | 换 Hub 通道时实现同样方法；业务层不导入执行器代码 |
| storage | 独立 SQLite、事务、追加事件 | 默认同主机；未来状态迁移单独实现 |
| artifacts | 流式取回、可信路径、签名与解码检查、原子归档 | 新媒体格式增加真实解析器与验收条件 |
| schemas / contracts | 对外契约源代码与 JSON 导出 | 修改后运行 export_contracts.py；主版本不兼容即拒绝 |

项目目录中的 Skill 不自动安装到 Codex 全局目录。总控读取 media-brief、image-prompt 或 video-storyboard 整理需求；程序读取请求模板与 media-review 政策，并将五个目录的哈希绑定冻结请求。文本知识帮助 Agent 决策，程序门禁负责执行约束；不依靠 Skill 自觉防止越权。

## 持久化与状态

`workflows.db` 的 workflows 表保存工作流完整 JSON，events 表追加有序状态事件。需求版本、冻结请求、审核记录、attempt、成品和人工复核都关联 revision。第一版采用文档记录而非拆分很多关联表，后续可迁移，不能直接修改冻结记录绕过审核。

通常状态链：draft → review_pending → ready_to_generate → generating → collecting → quality_review_pending → ready_to_deliver → delivered。拒绝进入 revision_required；执行失败保留 Hub 原始状态及 execution_uncertain。没有确认远端停止时取消保留 cancel_pending。

Hub 0.2.1 新增 waiting_for_user：映射为非终态 running，MediaFlow 保持原审核/生成步骤，另记 needs_user 与 intervention。普通 resume 查询原 task ID，不自动发送人工确认；用户明确处理完成后，human-resume 保存确认记录并通过 Hub resume_task 在原任务恢复。同一次介入响应丢失重用同键，不创建子任务或新的生成步骤。

提交前通过 SQLite `BEGIN IMMEDIATE` 保存完整参数、步骤及稳定 request_id；提交租约限制并发发送。租约过期可能重放原调用，因此真正不重复执行依赖 Hub 对同 request_id / 完整请求的持久化幂等。Hub task ID 回写后仅查询原任务。

审核通过记录必须来自绑定的审核 Hub task ID，并严格匹配 JSON schema、实际请求指纹和政策版本。最终文本、参数、参考快照、验收条件、生成器、执行模式、编译器和 Skill 版本参与指纹。任何相关修改需要新的需求版本与审核。总控操作者标识不影响生成内容。

生成执行成功后还必须拿到真实 media_artifacts。取回描述需与任务附件元数据一致；实际文件通过大小、哈希、签名、解码及请求格式/尺寸检查才进入质量复核。复核绑定文件哈希，交付再次校验文件。文本审核不证明画面效果；抽帧不证明完整视频质量。

视频探测器通过配置 `ffprobe_command` 提供，默认从 PATH 查找 ffprobe，也可指向项目内或系统的绝对路径，不依赖特定用户目录。MP4 探测扫描实际帧并拒绝解码错误、无视频流和零帧文件；优先使用视频流时长，避免较长音轨冒充较长画面。请求包含 fps 时核对平均帧率。工具缺失或无法启动返回明确错误，不能默默放过验证。

## 更换总控、Agent 和模型

新总控以相同 data_dir 启动，读取 handoff 和 show，再按 next_action 推进。不要求原聊天仍存在，不自动向其他聊天发送消息。

更换生成器时在配置启用新 agent / mode，并要求 Hub 提供实际模型能力、输入传输、参数范围和验收证据。MediaFlow 只调用通用 submit_task；执行器命令、会话、重试和附件发现由 Hub 适配器负责。改变生成器/模型后修订并重新审核，不能继续用旧通过记录。

当前编译器将结构化请求嵌入确定性文本模板；图片与视频模板独立。未来模型需要独有编译逻辑时在 domain 的编译边界增加 profile，而不修改存储、门禁或业务调用路径。

## Skill 和效果迭代

首轮真实二次元验收检查：角色特征、服装细节、肢体结构、构图、线条画风与目标一致性。单张通过不能证明跨图或跨镜头一致性，后续需固定角色设定/参考图后做少量对照样张。

把问题写成可观察缺陷，先改对应提示模板、角色设定、素材用途或参数，再跑新的经审核版本。模型更换是独立配置与能力决策。Skill 的文本调整容易；能否稳定提高效果必须以实际样张验证。
